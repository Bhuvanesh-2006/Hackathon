No embeddings, no vector database, no RAG

The project uses no embeddings model, no vector store and no retrieval step. The data is one table with 17 columns, so the full schema and every business rule fit in the prompt. Retrieval would add moving parts without improving answers, and the brief asked not to add vector databases without a real need. There is also no LangChain, LangGraph or multi-agent framework: the agent is a plain Python loop with fixed steps.

Pipeline 1: data preparation

backend/scripts/prepare_data.py, run once. Takes about a minute.

  1. Read both Excel sheetsRaw rows are cached as Parquet so later runs skip the 28-second Excel read.
  2. Normalise typesInvoice numbers and stock codes become text; customer IDs lose the trailing ".0" Excel adds.
  3. Remove the worksheet overlapConfirm the 1–9 Dec 2010 rows are identical in both sheets, then drop the second copy. This is the only removal.
  4. Classify every rowLine type (sale, cancellation, stock adjustment, zero price, bad-debt adjustment), item type (product, postage, fee, manual adjustment, discount, sample, test, gift voucher) and whether a customer ID is present.
  5. Add derived columnsline_amount (quantity × price), invoice month and year.
  6. Write the databaseTables transactions and dataset_metadata in retail.duckdb, about 20 MB.

Pipeline 2: answering a question

POST /api/agent/query. Runs on every question.

  1. Check the inputQuestion length, conversation ID format, and that the dataset is loaded.
  2. Ambiguity checkFixed rules catch phrasing like "best customers" and return a clarifying question with options.
  3. Load conversation contextThe last 4 turns from SQLite, so follow-ups like "now only for Germany" work.
  4. Build the promptFull schema, business rules and response instructions. Nothing is retrieved.
  5. Call the LLMReturns a plan: intent (answer, ask back, decline), SQL, explanation, rules used and a chart suggestion.
  6. Check the SQL with SQLGlotOne SELECT statement only; only the transactions table and its known columns; no file, system or settings functions. The query is rewritten from its parsed form, and that text is what runs and what the UI shows.
  7. Run itOn a shared read-only DuckDB instance with file and network access off and settings locked. Each query gets its own cursor. A timer stops it after 10 seconds; results are capped at 1,000 rows.
  8. Retry once on failureIf the check or the database rejects the SQL, the error goes back to the model once and the new SQL is checked again.
  9. Build the responseStatus is one of success, empty, clarification, unsupported, rejected or error. The summary is generated from the returned rows, so it cannot contain numbers the query did not return. The chart type is checked against the actual result columns.
  10. Save to historyQuestion, SQL, status, timings and up to 200 rows. API keys are never stored.

Pipeline 3: reliability benchmark

Run from the Benchmark page or python -m scripts.run_benchmark.

The 15 questions

  • 10 with a numeric answer: top products, monthly revenue, countries, cancelled value, cancellation count, returned units, missing customer IDs, postage, orders, top customers
  • 2 that must trigger a clarifying question
  • 1 that must return no data (revenue in 2015)
  • 1 unsupported (profit margin; there is no cost data)
  • 1 unsafe (delete cancelled invoices)

How answers are scored

  • Reference answers come from hand-written SQL on the raw columns, not the derived ones the agent uses, so a pass also checks the data preparation
  • Rows are matched by key regardless of order; numbers may differ by 0.5% or £0.51
  • Reported separately: overall pass rate, exact result match, SQL execution success, clarification success, unsupported and empty handling

Data rules applied

Defined once in business_rules.py and used by the prompt, dashboard, benchmark and UI.

TopicRule
CurrencyAll money in GBP (£). line_amount = quantity × unit_price
Period2009-12-01 to 2011-12-09. December 2011 is a partial month
Net revenueThe default meaning of "revenue": product sales minus cancellations
Gross revenueProduct sales before cancellations
CancellationsInvoices starting with "C". Subtracted in net revenue, reported separately elsewhere
ReturnsReturned units and number of return invoices are separate measures. Stock write-offs (3,393 lines with negative quantity) are not returns
Non-product codesPostage, fees, manual adjustments, discounts, samples, tests and gift vouchers are excluded from product revenue
Missing customer IDs235,287 lines (22.5%). Kept in totals, excluded from customer rankings, and stated in answers
Duplicates11,812 exact duplicates within a sheet are kept (they cannot be proven wrong) and counted in the Data Explorer

Safety layers

Each layer works on its own; the prompt is not relied on for safety.

LayerWhat it does
SQL validatorSQLGlot parse; one SELECT; table and column allowlist; blocks file, system and settings functions
Read-only databaseOpened read-only with external access off and settings locked. A test proves unchecked SQL still cannot write or read files
Limits10-second timeout, 1,000-row cap, 500-character questions, one SQL retry
LLM outputTreated as untrusted JSON. The model never runs code, shell commands or file operations
ErrorsShort messages with a code, no stack traces
SecretsAPI key read from the backend environment only; never sent to the browser or stored
